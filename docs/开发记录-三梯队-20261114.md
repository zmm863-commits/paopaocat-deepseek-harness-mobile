### 为什么走 loopback HTTP 而不是 `file://`

Drawnix 是 SPA：`index.html` 用**绝对路径** `/assets/*.js`，且模块脚本带 `crossorigin`。
`file://` 下绝对路径会解析到文件系统根目录（必然 404），`crossorigin` 模块也会被
浏览器安全策略拦。起 loopback 静态服务就都没问题 —— 这也是 App 已经用过两次的模式。

## 二 · 人声分离（MDX-Net）— ⚠️ 架构通了，音质未对齐

用户选的选型标准是**「体积可控」**：52.8 MB 的 `UVR_MDXNET_KARA_2`，而不是 316 MB 的 htdemucs。

### 架构（这部分是确定成立的）

```
Flutter (Dart)                 Rust (libmdx.so)              已有原生库
─────────────────              ─────────────────             ──────────
选文件 / 进度 UI   ──FFI──>    STFT → ONNX → iSTFT   ──dlopen──> libonnxruntime.so
  │                              │                              (1.28.2，sherpa 带的)
  └─ isolate 里跑（不卡界面）     └─ rustfft + ort
```

**关键决策：不额外打包 ONNX Runtime。** App 里已经因为离线配音（sherpa-onnx）带了
`libonnxruntime.so`（ORT 1.28.2，导出完整 C API，含 **NNAPI** 硬件加速）。Rust 侧用
`ort` 的 `load-dynamic` 在运行时 dlopen 它 ——
① 包体不增加；② 不会出现两个同名 `.so` 在 APK 里打架。

### 已经验证成立的

| 项 | 结果 |
|---|---|
| Rust 交叉编译 | ✅ `libmdx.so` 1.37 MB / ARM aarch64 / 符号 `mdx_open` `mdx_separate` `mdx_close` |
| ORT load-dynamic | ✅ `mdx_open -> 0`（桌面用同一套代码、Linux 版 ORT 验的） |
| 模型加载 | ✅ 178 节点 / 8 种算子 |
| 推理 | ✅ `mdx_separate -> 0`，**30 秒音频 8.4 秒**（桌面 x86_64 CPU） |
| 不崩 | ✅ inf/NaN 已加保护 + clamp |

### 踩到并解决的坑

1. **`ort` 的版本墙**：`BadVersion { version_str: "1.28.2" }`。
   根因不是 ORT 太新，而是 **ort 的默认 feature 递进启用到 api-31**（`MINOR_VERSION = 31`），
   而库是 1.28。修法：`default-features = false, features = ["load-dynamic", "api-28", "std"]`。
   ⚠️ 这个坑很隐蔽：只加 `api-28` 不改默认 feature **不生效**（可以 `cargo tree -f "{p} {f}"` 验）。
2. **feature 改了但没重编**：cargo 报 `Finished in 0.02s`。必须 `rm -rf` 整个 target。
3. **n_fft 不是 4096**：权威实现对 KARA_2 标的是 `mdx_n_fft_scale_set: 5120`。
   用 4096 会让频率轴整个错位（第一版跑出来幅度是原音频的 40 倍、人声伴奏几乎相等）。

### ❌ 没做完的部分（下一轮的输入）

**音质还不达标，缺的是「对齐权威实现的预处理」。** 具体缺三样：

| 缺什么 | 现状 | 应该怎样 |
|---|---|---|
| overlap-add 归一化 | 用常数 `1.5` | 权威实现是**边累加边记窗和**（divider buffer），最后逐点相除 —— 常数在首尾和变长块上会产生音量跳动 |
| 音频峰值归一化 | 没做 | demix 前把 mix 峰值归一到 1.0，demix 后用记录的系数还原 |
| chunk 的 trim 处理 | 没做 | 权威实现有 `trim` 概念，分块前后要裁/补 |

**验证素材也缺**：目前只用合成的正弦波（440Hz + 110Hz）验了"管线不崩"，
**没有用真实歌曲验过分离效果**。模型是训练在人声/音乐上的，对纯正弦波无意义。

### 包体

171.7 MB（122.1 → +49.6 MB = 压缩后的模型 + `libmdx.so`）

### 一个小决定

模型 `52.8 MB` 打在包里（离线可用），首次使用解包到私有目录（约几秒 + 占 52.8 MB 存储），
用"文件大小"做指纹判断要不要重解。

## 三 · 读 PDF — ✅ 换实现后完成（原方案 LiteParse 在 Android 不成立）

### 关键发现：LiteParse 这条路走不通（不是懒，是硬障碍）

LiteParse 的解析能力来自 **PDFium**（Chrome 的 PDF 引擎）。查了它依赖的
`run-llama/pdfium-binaries` 最新发布（`chromium/8085`）的全部资产：

```
linux-arm / linux-arm64 / linux-musl-x64 / linux-ppc64 / linux-x64 / linux-x86
mac-arm64 / mac-univ / mac-x64
win-arm64 / win-x64 / win-x86
wasi-wasm / emscripten-wasm
```

**没有 android。** 而且 `pdfium-linux-arm64`（3.6MB）链接的是 **glibc**，
Android 用的是 **bionic** —— 拿过来 dlopen 不起来。要自己编 PDFium 得拉
depot_tools、几 GB 依赖、几小时，为"读文字"这一个功能不值得。

### 换的方案：pdf.js（Mozilla，Apache-2.0，纯 JavaScript）

`pdfjs-dist` 6.5.438 的 legacy 构建在 node 里直接能跑，不需要 DOM / canvas。
实测能力**覆盖了 LiteParse 的核心**：

| 能力 | LiteParse | pdf.js 方案 |
|---|---|---|
| 文本提取 | ✅ PDFium | ✅ 实测中英文都对 |
| 文本坐标 | ✅ | ✅ x/y/w/h 全给（实测与 PDF 源里的 `72 700 Td` 完全吻合） |
| 表格结构 | ✅ 较好 | ⚠️ 差（只有坐标，表格要自己按坐标推） |
| OCR（扫描件） | ✅ 可选插件 | ❌ 没有 |
| 高质量渲染 | ✅ | ❌ 没有（node 下无 canvas） |
| **交叉编译** | **必须编 PDFium** | **零** |
| 体积 | PDFium ≈ 10-15MB native | 3.4MB JS（压缩后 0.7MB） |

对"让模型读懂 PDF"这个需求，前两项就是全部；后三项是另一个产品方向。

### 实现

| 文件 | 作用 |
|---|---|
| `app/assets/toolbox/parse-pdf.mjs` | 解析脚本：`--format md\|json`、`--pages 1-3`、`--out` |
| `app/assets/toolbox/vendor/pdfjs/pdf.mjs` | pdf.js 本体（1.1MB） |
| `app/assets/toolbox/vendor/pdfjs/pdf.worker.mjs` | worker（2.4MB） |
| `app/lib/ui/pages/read_pdf_page.dart` | UI：选 PDF → 显示读出来的文字 → 一键复制 |
| `app/lib/local/android_toolbox.dart` | 3 条部署映射（脚本 + vendor 目录结构要原样保留） |
| `app/lib/local/dsh_runtime.dart` | `parsePdfScriptPath` |
| `app/lib/ui/pages/media_page.dart` | 创作台「工具」组加「读 PDF」 |

### 关键实现细节

**1. 行要按 y 坐标聚，不能直接拼。**
PDF 里的文本块是一条条独立绘制指令，同一行会被切得很碎（中英文混排尤其明显）。
直接拼会变成 `Android上的真PPTX生成` 这种全糊在一起。脚本里按 y 聚行（容差取块高一半）、
行内按 x 排序、中文之间不加空格而西文之间加空格 —— 实测能还原成
`Android上的真PPTX生成`。

**2. pdf.js 的 warning 要静音。**
node 下它会抱怨缺 `@napi-rs/canvas`、`DOMMatrix`、`Path2D`、字体表 ——
这些**只影响渲染**，不影响文本提取。不静音的话用户会看到一堆红字以为坏了。

**3. 脚本也直接给模型用。**
会话里的模型可以自己跑：
`node "$DSH_ANDROID_TOOLBOX/parse-pdf.mjs" 文件.pdf`
不需要经过 UI 页面。

## 补记：2026-11-16 真机复查，两个新增功能原来是坏的

用户说「检查一下各个新增功能是不是真的可以用，比如人声分离，有出错信息」。
一查，**人声分离和读 PDF 在真机上都是坏的**。

### ① 第一个错（用户看到的）

```
音频解码失败：…/lib/arm64/libffmpeg.so":
library "libavdevice.so" not found: needed by main executable
```

**根因**：`libffmpeg.so` 自身依赖同目录的 `libavdevice.so` / `libavformat.so` /
`libavcodec.so` 等十几个库，而我在 `stemWorker` 里用 `Process.run` 直接 exec 它，
**没有设 `LD_LIBRARY_PATH`**。

App 里其他地方能跑 ffmpeg，是因为 `DshRuntime.environment` 里带了
`'LD_LIBRARY_PATH': nativeLibDir`。而这个新页面是另一条代码路径，漏了。

**同一个错也影响「读 PDF」**：它用 `Process.run(node, ...)` 起 node，
`libnode.so` 同样依赖同目录的 `libc++_shared.so` / `libicu*`，一样会挂。

**修**：两处都补 `environment: {'LD_LIBRARY_PATH': runtime.nativeLibDir}`。
人声分离跑在 isolate 里拿不到 runtime，所以把 `nativeLibDir` 作为一个字段
（`StemTask.ldLibPath`）传进 isolate。

### ② 第二个错（修完第一个才会撞上）

`ort::init_from("libonnxruntime.so")` 在手机上必然失败。

**根因**：Android 的 bionic 链接器**从 API 21 起不再读 `LD_LIBRARY_PATH`
去找 dlopen 的裸库名**，只认绝对路径（或由 `System.loadLibrary` 预加载）。
桌面上我验收时是用 `MDX_ORT_DYLIB` 传的绝对路径，所以没暴露。

**修**：`mdx_open` 加第二个参数 `ort_dylib`，由 Dart 侧传
`<nativeLibDir>/libonnxruntime.so`。桌面那条路径继续走环境变量，两边同一份代码。

### ③ 顺带清掉一段死代码

`StemSeparator.separate()`（早期的**同步版**）已经没有任何调用者——页面走的是
`stemWorker` + isolate。它也是唯一一处会卡主线程的长调用，一并删了，
连带删掉只给它用的 `_tail` / `_baseName`。

### 教训（写给自己）

**新功能只要走了一条新的进程启动路径，就必须自己带全环境变量。**
`DshRuntime.environment` 是给"会话进程"用的，别的代码路径抄不上——
这次两个功能一起坏，根子都是"以为设置了"。

**每一个 FFI 加载的原生库，在 Android 上都要用绝对路径。**
桌面上用 soname 能跑，是桌面链接器读 `LD_LIBRARY_PATH`；Android 不读。
