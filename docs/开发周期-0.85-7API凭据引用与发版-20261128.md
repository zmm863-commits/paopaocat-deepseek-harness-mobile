# 开发周期 0.85 —— 一个厂家名废掉所有模型（含 0.85 发版记录）

> 2026-11-28 | 版本：v0.84（255）→ v0.85（256） | 触发：三份真机 `dsh-report`
> （2026-11-18 华为 ELS-AN00 / Android 12；2026-11-27 华为 SPN-AL00 / Android 10）

## 1. 一句话结论

用户把厂家命名成「**7API**」，我们据此生成的环境变量名是 `7API_API_KEY` ——
**以数字开头**，不满足引擎的凭据引用规则 `^[A-Za-z_][A-Za-z0-9_]*$`，
`credentialRef()` 直接抛 TypeError → `resolveProfiles()` 整次失败 →
**整条 `llm-pi-ai` 插件不激活** → 所有厂家都没有适配器 → `session/new` 只回
`Internal error`，而且报的是**另外一个**厂家的名字。

同一个用户还撞上三件独立的事：本地 Office 工具探活静默失败、Bot 页「选择工作区
目录」在老 WebView 上报 `AbortSignal.any is not a function`、诊断报告把数字全打码
（结论就藏在那几个被打掉的数字里）。0.85 把这四条一起修了。

## 3. 机制：为什么一条坏配置能带走整张表

运行包里的 `@deepseek-ai/dsh-llm-pi-ai/lib/index.js`：

```js
function invalid(provider, detail) {
  throw new PiAiCatalogError(`llm-pi-ai: provider "${provider}" ${detail}`);
}
```

`resolveProfiles()` 逐条检查 provider 配置，命中任意一条就调用 `invalid()` ——
**是 throw，不是 skip**。于是：

```
一条坏配置 → resolveProfiles 抛错 → llm-pi-ai 整条插件激活失败
          → 所有厂家都没有适配器 → session/new 只能回 Internal error
```

它会拒的（照抄自运行时代码，别凭印象改）：

* `provider "x" has an empty baseURL`
* `model "id" has an empty id`
* `lists model "id" more than once`
* `model "id" needs an api; the installed catalog does not describe it`
* `model "id" contextWindow must be a positive integer`
* `credential ref "…" must match /^[A-Za-z_][A-Za-z0-9_]*$/`
* 已删除字段（`provider` / `maxRetries` / `maxRetryDelayMs`）一出现就抛

## 4. 为什么这件事"反复在模型配置上"出现

不是运气差，是三个结构性原因：

1. **全有或全无**：整张表交给一个插件，任一条坏就整表不激活（上面那段代码）。
2. **手拼 YAML、写前几乎不校验**：0.85 之前只有两条手工条件（有模型、baseURL 非空），
   其余全靠"记得"。这次撞上的 `7API` 就是既没被挡住、也没被预见的那个。
3. **规则在上游、会变**：`rejectRemovedFields()` 已经删过两轮字段，我们手写的配置
   **天然会随运行时升级而过期**。

历史事故（同一族，每修一次只是补上一种坏法）：

| 时间 | 坏法 | 后果 |
|---|---|---|
| 2026-10-10 | 轮换池名叫 `001` | YAML 把裸数字读成整数 → 校验拒 → 2 条 entry 没激活 → 全部模型不能用 |
| 2026-10-17 | opencode-go 不写 `api` | `needs an api` → 会话建不起来 |
| 2026-11-05 | 留了一个 0 模型、baseURL 空的厂家 | 同一句话：所有厂家都没有适配器 |
| **2026-11-27** | **厂家名以数字开头（7API）** | **凭据引用非法 → 整表不激活** |

## 5. 0.85 修的六条

### 5.1 凭据变量名永远合法

`app/lib/data/configured_models.dart`

* `envNameFor()`：推导出的名字**必须以字母/下划线开头**，数字开头加 `P` 前缀
  （`7api → P7API_API_KEY`）。
* 新增 `normalizeApiKeyEnv()`：读盘时把**存量**用户 models.json 里的非法值就地改名
  （真机那份里就是 `7API_API_KEY`）。Key 存在安全区、按 **provider id** 取，改名不丢 Key。
* `credentialRefPattern` 把引擎那条正则摆出来，供校验器和测试共用。

### 5.2 写 overlay 之前先校验（新文件）

`app/lib/data/model_overlay_rules.dart` —— 纯函数，规则逐条对应运行时源码：

| 情况 | 处理 |
|---|---|
| 模型 id 重复 | 只留第一个（运行时会整表拒绝） |
| `contextWindow` ≤ 0 / 过小 | 兜底 1000000 / 抬到 1024 |
| Base URL 空 / 不是 http(s) | **整条厂家丢掉** |
| 协议不认识 | 回落 `openai-completions` |
| 凭据引用非法 | 整条丢掉（正常路径已被 5.1 规整，这里是兜底） |
| 空模型 id / 空 apiKeyEnv / 重复厂家 | 丢该条 |

`dsh_runtime.dart` 接上之后，overlay 日志里的「厂家数 / 模型数」也改成**按真正写进去的算**
—— 之前数的是 `config.models`，被去重和丢掉的也算进去，日志会撒谎。

### 5.3 工具箱脚本不再静默退出 0

`app/assets/toolbox/{mcp-office,make-docx,make-xlsx,read-xlsx}.mjs`

四个脚本最后那句"是不是被直接运行"的判断原来是 URL 全等：

```js
const isDirectRun = process.argv[1]
  && import.meta.url === pathToFileURL(resolve(process.argv[1])).href;
```

路径只要差一点（软链 / realpath / 前缀不同）就判成"被 import 进来"，于是
`serveStdio()` / `main()` 根本不执行，进程 **exit 0、两路零输出**。改成文件名兜底
（`make-pptx.mjs` 在 10-20 就已经是新写法，另外四个没跟上）。

> ⚠️ 踩坑记录：第一版顺手加了"判不出来但带参数就大声报错 + exit(2)"。
> 结果 `mcp-office` 会 `import read-xlsx`，被 import 的那个模块拿到宿主的参数
> （`--selftest`），于是**把宿主进程 exit(2)**。已撤掉这条分支 ——
> 被 import 时保持安静才是对的。

### 5.4 老 WebView 兼容补丁

`app/lib/ui/pages/bot_page.dart` —— `onPageStarted` 里、上传 hook 之前注入
`_compatJs`，一次补 7 个 API：

`AbortSignal.any`(116) / `AbortSignal.timeout`(103) / `Promise.withResolvers`(119) /
`Object.hasOwn`(93) / `structuredClone`(98) / `Array.findLast`·`findLastIndex`(97) /
`crypto.randomUUID`(92)。补了哪几个会写进诊断日志。

### 5.5 报告 KEY 段不再把数字打码

`app/lib/local/diagnostics_log.dart` —— `normalize()` 会把所有数字换成 `#`，
那是**聚合 key** 用的；之前却拿它当展示文本，于是 `HTTP 400 → HTTP #`、
`7API_API_KEY → #API_API_KEY`、`180 秒 → # 秒`，**诊断结论就藏在被抹掉的数字里**，
只能在几百行明细里翻原文。现在展示走 `normalizeForDisplay()`（只压空白 + 截断），
聚合仍按数字归一。

### 5.6 更新源加第三条 Gitee 线路

`app/lib/local/update_source.dart` —— 原来两条都是 GitHub 系（raw + jsDelivr），
被 reset 时会**一起**挂。现在 `raw → jsDelivr → Gitee` 三条并发、谁先回用谁。

## 10. 一条方法论

**"错误信息里没有名字"比"错误本身"更贵。** 这次三份日志里，最值钱的两句都不是
UI 上的报错，而是 stderr 里那行 `credential ref "7API_API_KEY" …` 和报告 KEY 段
原本能显示、却被自己打码掉的数字。所以 0.85 的修复一半在"让它不坏"，另一半在
"坏了要说出是谁"—— 那 7 个凭据/校验规则，本质是把"引擎会说的话"提前搬到我们这边。
