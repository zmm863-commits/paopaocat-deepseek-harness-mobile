## 二、Bug 修复

### 2.1 轮换池：一个空组连坐所有组

**现象**：「轮换池中间有无法使用的模型，会造成整个轮换池无法使用」。

**根因**（两层）：

```
用户组里唯一的模型被上游收回 / 厂家被删
        ↓
Dart 侧 _buildGroups 逐个 continue 跳过 → 该组 members 变成 []
        ↓
代理 validateConfig 遇到空数组 → die() → process.exit(2)
        ↓
整个代理进程没起来 → 所有组一起不可用
```

**修法**（三处）：

| 位置 | 改法 |
|---|---|
| `rotate-proxy.mjs` | 空组**跳过并记日志**，不再退出；全部组都空才报错，且给一句能指导用户的话 |
| `rotation_proxy.dart` | 组装时剔除空组 + 把「哪个成员、为什么没了」写进诊断日志；全空则不起代理返回 null |
| 同上 | 新增 `skippedGroups` getter，让「池子不好使」变得可解释 |

**验证**：命令行级复现对照 —— 改前 `exit code=2`（代理根本没监听）；改后输出「已跳过 1 个没有可用成员的组：empty（其它组不受影响）」，好的那组返回 **200**，进程存活。

### 2.2 轮换池：代理没起来也写 `rotate` 厂家

**根因**：`writeOverlayFromConfig` 的条件是 `if (groups.isNotEmpty)`，端口兜底到固定的 `39321`。于是代理没起来时，overlay 里仍有一个指向死端口的厂家 —— 用户选中那个组只会收到 `connection refused`。

**这与这份周期里反复出现的是同一个病：配置里有 ≠ 服务在。**

**修法**：条件改成 `groups.isNotEmpty && rotatePort != null`；删除 `rotateBasePort` 常量（断掉"兜底到固定端口"这条路）。

**验证**：新增测试「没有代理端口时不写 rotate 厂家」，并修正 2 条旧测试（契约变了：必须传端口才写）。

### 2.3 自己添加的厂家在设置里不可见

**现象**：自定义模型「只能在会话选择器和轮换池里看到」。

**根因**：设置页「我的模型」只遍历 `myModelProviders()`（内置四家 + Agnes）。自定义厂家只存在于 `models.json`，于是它可用、能进池子、却看不到也删不掉。

**修法**：新增 `_customProviders()` + `_customProviderCard()`。

**关键取舍：没有复用内置卡。**

内置卡展开后的「测试并保存」会按内置预设**重写 provider 记录**。而自定义厂家的 `api`（`openai-completions` / `anthropic`）是用户当初选的 —— 走那条路会被静默改回默认值。

所以新卡**只碰 Key 和删除**，绝不碰记录本身。

**验证**：新增 widget 测试「自己添加的厂家也在设置里」（断言厂家名可见、展开能看到模型、地址显示）。

### 2.4 「后台运行」只弹 AOSP 那个页

**根因**：只用了 `ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`。而 vivo 在 OriginOS 上会在 App 离开屏幕后**直接掐断网络** —— 不开「允许后台高耗电」照样断，那个系统框管不到。

**修法**：新增 `VendorSettings.kt`（厂商识别 + 三张页面表 + 详情页兜底），UI 改成三道关清单。

**两道必须做的校验**：

```kotlin
val info = runCatching { intent.resolveActivityInfo(pm, 0) }.getOrNull()
if (info?.exported != true) continue    // 不导出的 activity 直接 startActivity 会抛 SecurityException
```

少了这道检查，报错被 catch 掉 = 用户点了**没有任何反应**，最难查。

**设计取舍：界面上不打勾。**

厂商开关的状态系统**不告诉 App**。所以只写「已送你去过设置页，回来确认一眼」，用四态（绿/红/灰/去过）而不是对勾。打勾就是替系统撒谎。

### 2.5 切 Bot 页闪 `setState during build`（真机发现）

**现象**（2026-11-01 真机 logcat）：切到 Bot 页时刷 `setState() or markNeedsBuild() called during build`，指向 `AppShell._onSchedulesChanged`。

**根因**（三环连起来）：
```
didUpdateWidget（处于 build 阶段）
  → _store.load()（标了 async 但函数体**没有 await** → Dart 同步跑完整个函数）
    → notifyListeners() 同步触发
      → AppShell 监听器 _onSchedulesChanged 里 setState()
        → build 中途改树 → 异常
```

**修法**：`scheduled_page.dart` 的 `didUpdateWidget` 里把 `_store.load()` 推到 `addPostFrameCallback`——build 结束后再加载，`notifyListeners` 就不会落在 build 阶段里。

**验证**：重新编译 + 装机（01:10:53），启动后 logcat 搜 `setState() or markNeedsBuild` → **0 次**。

### 3.2 Kilo 第二免密上游

**背景**：OpenCode 那条的免费额度会耗尽（本周期实测到 `429 FreeUsageLimitError`）。单上游 = 单点。

**做法**：同一端口用路径前缀分流，注册成第二个厂家。

```
/v1/*        → Zen（OpenCode，需要伪装成官方 CLI，否则 403）
/kilo/v1/*   → Kilo AI 公共网关（免 Key，也不需要伪装）
```

**实测**：`GET /kilo/v1/models` → 17 个 `isFree` 模型；用 `dots-studio/dots-3-note-preview:free` 发真实对话，模型回了「收到」。

**关键设计**：Kilo 不做 `applyGate`（那是 Zen 的商用改造：强制 stream、注入门禁工具、工具名归一）。对公共网关做改造反而可能被当成异常客户端。

### 3.3 按响应体形状判流式

**问题**：上游高负载时会把**完整 SSE 帧序列**用 `application/json` 的 header 发回来。直接沿用这个 header → 下游按 JSON 解析 → 整轮失败，而且失败得极像"模型坏了"。

**修法**：先读一小块看形状，再决定告诉下游是什么。

**最容易写错的地方**：嗅探读走的那一块必须补发，否则每轮都会悄悄丢掉开头 1KB，表现是"回复总是从中间开始"。测试专门钉了这条。

### 3.4 会话映射持久化

**为什么**：免费额度按**会话**计。代理一重启（冷启动、被系统回收后拉回），内存映射就空了 → 同一对话被当成新会话 → 额度白花。

**为什么不能直接存 seed**：seed 是用户的**第一条提问原文**。落盘就是把它留在手机上。

**修法**：存 `sha256(seed)` → session id，只能做映射，反查不出原文。

**验证**：发请求 → 落 2 条 → 重启 → 日志「已恢复 2 条会话映射」。

### 3.5 最近的改动

**解决什么**：agent 一口气改了十几个文件，然后说"已完成"。用户的问题是「改了哪些？」

**为什么不用 git**：手机上没有 git 可执行文件（运行时只带 node）。而用户真正想知道的是「刚刚这几分钟」，**用文件修改时间回答更直接**。

**三条克制**：

- 跳过 `node_modules` / `.git` / `build` / `.dart_tool`；跳过隐藏文件与空文件
- 4000 条硬上限 —— 打开面板卡三秒比看不到更糟
- 扫描失败不整块报错：权限不足、目录被移走、扫到一半文件被删，都是"跳过这一个继续"

**不做 diff**：做不了真 diff，而"假装做"要自己存历史副本 —— 那会占空间、还会弄乱工作区。只回答"哪些文件"，点到为止。

### 3.6 备份与换手机

**需求**：用户换手机时把数据带过去。

**只解决一件事**：把 App 的数据变成一个**加密文件**，以及从它恢复。

| 数据 | 迁移 | 理由 |
|---|---|---|
| `sessions/` | ✅ | 历史对话，最值钱 |
| `workspace/` | ✅ | 用户文件 |
| `models.json` / `experts.json` / `memory.json` / `local_chat.json` / `workspaces.json` | ✅ | 配置与记忆 |
| `dsh/`（运行时 106MB） | ❌ | 新机装完自己解包 |
| `toolbox/` `shims/` | ❌ | 跟着 App 包走 |
| `bridge.json` | ❌ | 含桌面平台访问口令，且与设备绑定 |
| **API Key** | ❌ **物理上迁不了** | 存在 Android Keystore，密钥与设备硬件绑定 |

**格式 `.pcbak`**：

```
0     4      Magic "PCB1"
4     16     salt（scrypt）
20    12     iv（AES-GCM）
32    16     auth tag
48    ..     密文（里面是普通 zip）
```

用 GCM 而不是 CBC：GCM 自带完整性校验 —— 密码错、文件被改、传输截断，都在解密那一刻报错，不会拿到半个损坏的包去覆盖数据。

**三个安全设计**：

1. **密码走 stdin，不进 argv** —— `/proc/<pid>/cmdline` 同 uid 可读，手机上一个恶意 App 扫进程列表就能看走密码。
2. **恢复前自动留退路** —— 先把当前数据打成 `导入前-*.pcbak`，安全备份失败就**不继续**（宁可这次导入不成，也不能让用户在没有退路的情况下覆盖）。
3. **防目录穿越** —— 包里写 `../../evil.sh` 时跳过（解压类功能最经典的洞），已用恶意包实测过。

**为什么整件事在 node 侧做**：AES-GCM 和 scrypt 是 `node:crypto` 自带的，zip 用已有的 `office-zip.mjs`。Dart 侧要引 `cryptography` 包才能做同样的事，而手机上没有 npm。

**核实过的依赖**：

| 包 | 缓存里 |
|---|---|
| `archive` | 有（但没用上，改走 node 侧） |
| `http` | 有 |
| `cryptography` / `pointycastle` | ❌ 没有 |

## 四、关键决策（为什么 **不** 这么做）

这一节比"改了什么"更重要 —— 它记录的是否决理由，避免下次重新论证。

### 4.1 为什么不开放插件安装（P2）

**用户 2026-10-31 决定：暂不开放。**

插件跑在 DSH 进程内 = 任意代码执行。Android 的沙箱按**应用 UID** 分，插件与 DSH 共用同一个 UID，**App 层没有沙箱能挡住它**。

所谓"安全校验"只能放在**装之前**（来源 + 哈希），装之后没有兜底。

设置页保持「暂未开放」占位。若日后重启，建议档位：

| 档位 | 做法 | 评价 |
|---|---|---|
| A 白名单 | 只装内置清单 | 最安全，生态 = 0 |
| **B 来源 + 哈希** | 用户选 tgz，校 sha256 | **推荐** |
| C 任意 npm | 自动拉依赖树 | 做不到（手机没有 npm） |

### 4.2 为什么不接网盘直连

**成本不是问题**：一年换机一次 × 1 万用户 × 3 个请求 = 3 万请求/年，Cloudflare Workers 免费额度是 10 万/天。

**真正的成本是维护**：多一个服务 = 多一个会挂的东西，而它挂的时候恰好是用户刚换手机、最慌的时候。

**而且用户不缺传文件的工具** —— 微信、QQ、网盘 App、数据线，他们每天在用。App 只需要「变成文件」和「从文件恢复」。

**用户群现实（2026-10-31 调研订正）**：用户主力是**百度网盘**与**夸克网盘**，坚果云/群晖这类 WebDAV 少有人用 —— 所以"接 WebDAV"对多数用户等于没接。

两家的 API 现状（调研结论，写清楚免得重复查）：

| 网盘 | 官方 API | App 内直传可行性 |
|---|---|---|
| **夸克** | **没有公开开放 API**（官方不提供）；市面工具都是抓 web 端私有接口 | ❌ 逆向接口随时变、违反服务条款，**不做** |
| **百度** | 有开放平台（OAuth 授权），需注册应用 | ✅ 技术可行；但需你去审核拿 `client_id`，且 secret 在客户端有被封风险 |

**结论：对百度/夸克用户，"文件方式"恰好就是最适配的，不需要接任何 API。**

- **备份**：导出 `.pcbak` → 系统分享面板 → 选「百度网盘」/「夸克网盘」App → 存入
- **恢复**：网盘 App 里下载该文件 → 系统文件选择器选它 → 导入

他们的网盘 App 都注册了 Android 的分享接收与文件提供能力，第一期的文件方式**已经走通**这条链，零额外代码。

**分期计划（订正）**：

```
第一期  导出/导入文件              ✅ 已完成，且恰好是百度/夸克用户的最优路径
第二期  百度网盘直传（OAuth，你去审核）  ← 可选，省"分享/下载"两步
夸克    无法 App 内直传（无官方 API），永远走文件方式
```

即：**换机迁移问题已经通过第一期解决**；第二期只是"省两步点击"的锦上添花，不是必需品。

### 4.3 为什么「最近改动」不用 git、「备份」不用 Dart 加密

同一个原则：**能用已在的东西，就不引入新依赖**。手机上没有 npm，多一个依赖就多一个装不上的可能。

### ✅ 2026-11-01 编译验证已完成（手机真机 40599）

**全部 Kotlin 改动已通过编译器并装机验证**，版本 `0.0.81 → 0.0.82`。

编译方法（在有 Android SDK + Flutter 的机器上）：
```bash

mkdir -p /tmp/dshbuild && cd <项目>/app
cp -a lib assets pubspec.yaml pubspec.lock analysis_options.yaml /tmp/dshbuild/

# 2. 编译（需国内镜像，见下方两条）

export PUB_HOSTED_URL=https://pub.flutter-io.cn
# Maven 依赖走阿里云：~/.gradle/init.d/mirror.gradle（settingsEvaluated + allprojects 重定向）
cd /tmp/dshbuild && flutter build apk --debug --target-platform android-arm64
# 3. 装机（adb mdns 无线调试，端口会变，先 mdns services 查）
adb connect <ip>:<port> && adb install -r app-debug.apk
```

**编译时抓到的真实错误**（这就是"必须编译验证"的价值）：
- `MainActivity.kt` 有两个同名 `openAppSettingsPage()`：一个 `Unit`（新加）、一个 `Boolean`（原有）→ Kotlin `Conflicting overloads`。已删掉重复定义，调用处改用原有 `Boolean` 版（内部已 try/catch，不抛异常）。

**国内镜像两个坑**（不配会卡死/极慢）：
1. `google()`/`mavenCentral()` 直连会**卡死在 SSL read**（无超时、30 分钟零字节）→ `~/.gradle/init.d/mirror.gradle` 重定向到阿里云 + `systemProp.org.gradle.internal.http.connectionTimeout/socketTimeout`。
2. Flutter engine artifacts（`storage.googleapis.com`）不走 Maven，直连 ~42KB/s → `FLUTTER_STORAGE_BASE_URL=https://storage.flutter-io.cn`，编译从 20+ 分钟降到 40 秒。

## 八、构建坑：runtime 拷错导致包从 118MB 涨到 238MB（2026-11-01）

## 九、本地推理引擎评估：MNN（2026-11-02）

### 起因

用户提出「把现有的本地推理引擎替换为 MNN，因为以前的用得不太好」。

### 先把「用得不太好」查清楚了

两件事，都不是"慢"：

1. **llama.cpp 在这台手机上必然段错误**（`local_model_server.dart:518` 的真机证据）：骁龙 8 Elite / Armv9.2，CPU、GPU、NPU **全都 `code=-11`**；27 tokens 的短自检能过，长请求必崩。
2. **而且当前 APK 里根本没有引擎**：`libllamaserver.so` 要显式 `DSH_ANDROID_INCLUDE_LLAMA=1` 才打包，我这几次出的包都没设 → 本地模型页只会提示「引擎不存在」。

### MNN 的调研结论

| 维度 | 结论 |
|---|---|
| 是什么 | 阿里巴巴的 C++ 端侧推理引擎（Apache-2.0，16.3K★，**不是 DSH 插件**） |
| Android 预编译 | 有：`mnn_3.6.2_android_*_cpu_opencl_vulkan.zip`，arm64 全套 **10MB**，含 `libllm.so` |
| HTTP API | 官方 `mnncli serve` 提供 **OpenAI 兼容 + Anthropic 兼容**，正是 DSH 要的形状 |
| 好处 | 阿里自家引擎，对国产 SoC 适配通常更好；体积比 llama.cpp 小 |

### 官方 mnncli 的两个硬伤（实测，不是推断）

1. **CMakeLists 引用了不存在的文件**：Android 分支 append `src/AndroidVideoDecoder.cpp`，该文件**在 git 历史里从未存在** → configure 阶段直接失败。
2. **强依赖 OpenSSL**：`model_downloader` 用 `openssl/sha.h` + `httplib::SSLClient` 做 HTTPS 下载，交叉编译必须先把 OpenSSL 也编一份给 Android。

### 最终做法：自己写最小 server（不修 mnncli）

理由：我们只需要**本地推理**（模型手动推进手机、只听 127.0.0.1），HTTPS 下载器/视频解码完全不需要。

产出 `/tmp/mnn-mini/mnn_mini_server.cpp`（~280 行），实现：
- `GET /v1/models`、`POST /v1/chat/completions`（OpenAI 兼容，流式/非流式）、`GET /healthz`
- 直接用 MNN 的 `Llm::createLLM/load/response` + 自带的 `httplib.h`
- 手写极简 JSON 取值，不引第三方库

**编译验证通过**：

| 项 | 结果 |
|---|---|
| MNN 静态库 | `libMNN.a` 235MB（`MNN_BUILD_LLM=ON`，LLM 已合并） |
| 最小 server | 编译成功，**strip 后 4.9MB**，`ELF 64-bit ARM aarch64 PIE` |

**过程中解决的坑**：
- MNN 3.6.2 的 CMake bug：`MNN_SEP_BUILD=OFF` 时 `llm` 是 OBJECT 库，不允许 `POST_BUILD` → 用 `-DMNN_BUILD_FOR_ANDROID_COMMAND=ON` 绕过。
- OpenSSL 源码 clone 反复失败（git 只拿到空 `.git`）→ 直接放弃 OpenSSL（自己写 server 不需要）。

## 十二、模型清单扩容：接入 MNN 官方模型市场（2026-11-02）

### 市场里有什么

| 类别 | 数量 |
|---|---|
| `models`（对话/多模态） | **159 个** |
| `tts_models` | 2 |
| `asr_models` | 2 |

按厂商：Qwen 61 · LFM 21 · Smol 11 · Gemma 10 · DeepSeek 6 · Llama 6 · Hunyuan 5 …
按体积：**<1GB 有 34 个**、1-2GB 33 个 —— 适合手机的有的是。

字段里有 `sources`，同时登记 **HuggingFace 和 ModelScope** 两个源。

### 关键发现：文件构成不统一，清单必须动态生成

不同 MNN 模型的文件构成**不一样**：

| 模型 | 特殊之处 |
|---|---|
| Qwen3-1.7B | 没有 `llm.mnn.json`，分词器是 `tokenizer.txt` |
| Qwen2.5-Coder-1.5B | 有 `llm.mnn.json`，分词器是 **`tokenizer.mtok`**（不是 .txt） |
| 部分小模型 | 多一个 `embeddings_bf16.bin`（单独几百 MB） |

所以**写死文件清单必然出错**。mnncli 也是动态问 API 拿的（源码里没有硬编码文件表）。

### 做法：写生成脚本（`install/models/gen-mnn-manifest.mjs`）

```
model_market.json（挑模型）
  → ModelScope API: /api/v1/models/MNN/<repo>/repo/files
  → 过滤文档文件 → 主文件=最大的那个，其余进 companions
  → 自动带每个文件的 **真实 sha256**
```

**为什么用 ModelScope 而不是 hf-mirror**：
- ModelScope 是阿里官方，国内直连快且稳（MNN 市场里登记的源之一）
- **API 直接返回 sha256** —— 正好补上我们清单里长期缺的哈希

## 十七、会话调不通的真正原因：流式少了一帧（2026-11-03）

用户反馈「还是不能用」。真机日志给出确切错误：

```
[chat] prompt failed: session/prompt 失败：Internal error:
       turn failed: Stream ended without finish_reason
```

**加载（转圈）修好了，但会话还是不通** —— 这是**两个独立的 bug**。

### 修①：`/health`（上一轮已修，本轮确认生效）

| 修前 | 修后 |
|---|---|
| App 探 `/health` → 404 → **90 秒超时** | **12 秒就绪**，`{"status":"ok","ok":true,...}` |

真机点「启动」实测：**第 1 次轮询（12 秒内）就返回就绪**。

### 修②：流式响应缺 `finish_reason`（本轮新发现）

对照 **MNN 官方 `mnncli_server.cpp`** 的实现，它发三段：

```
① 正文帧：delta.content = 全文，finish_reason = null
② 收尾帧：delta = {}，finish_reason = "stop"      ← 我原来缺这一段
③ data: [DONE]
```

我原来只发 ①③。DSH 的流解析器一路等到流结束都没见到 `finish_reason`，
于是把整轮判成失败 —— **用户看到的就是"发消息没反应"**。

**修**：按官方格式补齐三段。真机 curl 验证输出：

```
data: {"id":"chatcmpl-mnn-...","object":"chat.completion.chunk",...,"finish_reason":null}]}
data: {"id":"chatcmpl-mnn-...","object":"chat.completion.chunk",...,"finish_reason":"stop"}]}
data: [DONE]
```

### 顺带修③：多轮上下文（之前每轮都失忆）

原来只取 `messages` 里**最后一条 user** 传给引擎 → 第二轮起完全不记得上一句。

查 MNN 源码：`Llm::response(const ChatMessages&)` 会把**整段对话**渲染，

## 十八、「很慢，无法正常使用」——改成真流式（2026-11-03 上午）

用户：「很慢，无法正常使用」。

### 根因：首字延迟 = 整个生成时间

我原来的流式是**假的**：等 `llm->response()` 把整段生成完，再一次性发一帧 SSE。
所以用户发一句话，屏幕上**几十秒什么都不动**，然后「啪」一下全出来 ——
这就是「慢」的体感来源（模型其实一直在算，只是没人告诉界面）。

### MNN 本身支持真流式

查源码 `transformers/llm/engine/src/speculative_decoding/generate.cpp`：

```cpp
auto decodeStr = mLlm->tokenizer_decode(mContext->current_token);
if (nullptr != mContext->os) {
    *mContext->os << decodeStr;
    *mContext->os << std::flush;     // ← 逐 token 吐
}
```

`Llm::response(..., std::ostream* os)` 每解出一个 token 就 `<<` 一次。

**官方 `mnncli` 的接法**（`apps/mnncli`）：
1. 自定义 `LlmStreamBuffer : std::streambuf`，`xsputn()` 里回调
2. `Utf8StreamProcessor` 按 UTF-8 字符切（避免半个汉字发出去）
3. 每凑齐一个字符就推一帧 SSE，`finish_reason` 在最后一帧给 `"stop"`

### 我的实现

| 组件 | 做法 |
|---|---|
| `LlmStreamBuffer` | 自定义 streambuf，`xsputn`/`overflow` 里把字节交给回调 |
| UTF-8 拼字 | 按首字节判断字符长度，凑齐一个完整字符才发（**否则汉字乱码**） |
| 传输 | `res.set_chunked_content_provider(...)`，每帧立刻 `sink.os.flush()` |
| 收尾 | 正文帧 → `finish_reason:"stop"` 帧 → `[DONE]`（**三段缺一不可**） |
| 生成/非生成共用 | 抽成 `runGenerate(std::ostream*)`，两条路走**同一条推理代码**，不会出现"流式对、非流式错" |

### 另一个性能发现：线程数

可以按 CPU 核数传 `thread_num` 试试（下一轮验证）。

## 二十二、App 更新加速：dsh.ppcat.online（2026-11-03 晚）

用户反馈「有用户说用 App 的更新太慢」，问隧道能不能加速。

### 先查清两件事

**① 现在从哪下**：`update.json` 里的 `url` 指向 GitHub Releases，包体 **118MB**。

**② 隧道有没有空间**：没有。隧道只是反向代理通道，文件始终在本机硬盘。

现有 `ppcat.online/1GOrQleatZtGEYOF/*` 指向的是：

```
python3 -m http.server 8917 --directory exposed
工作目录：/root/软件应用工程区/node-hunt/exposed/
```

**而且它不支持 Range**（实测返回 200 + 整个文件，不是 206 + 片段）——
118MB 单文件若不能断点续传，断一次就得从头来，这在蜂窝网络上是灾难。

### 配了什么

| 环节 | 做法 |
|---|---|
| 静态服务 | 新写 `node serve.mjs`（端口 8919），**支持 Range / HEAD / 目录穿越防护** |
| 文件目录 | `/root/办公/dsh-update/<16位随机路径>/` |
| 隧道 ingress | `dsh.ppcat.online` + path `^/<随机>/.*` → 127.0.0.1:8919 |
| DNS | `cloudflared tunnel route dns paopaocat dsh.ppcat.online` |
| 更新清单 | 隧道版 `update.json`（url 指向隧道，sha256 已算） |

**为什么用随机路径**：不给人扫到就下 118MB 的机会——那会吃光本机上行。
无密钥路径实测返回 404。

### 最大的坑：7844 端口被封

隧道一开始怎么都起不来，`cloudflared` 报：

```
Failed to dial a quic connection: timeout: no recent network activity
DialContext error: dial tcp 198.41.192.37:7844: i/o timeout
```

**根因**：这台机器的出站**只放行 443 一类常见端口**，而 cloudflared 连
Cloudflare 边缘用的是**硬编码 7844**，没有自定义端口的参数。

实测矩阵：

| 目标 | 端口 443 | 端口 7844 |
|---|---|---|
| 104.16.123.96（CF 普通站点） | ✅ 通 | ❌ 不通 |
| 198.41.192.x（CF 隧道边缘） | ❌ | ❌ |
| github.com | ✅ 通 | — |

**解法**：`--edge-ip-version 6 --protocol http2`

IPv6 的出站策略与 IPv4 不同，7844 走 IPv6 是通的：

```
Registered tunnel connection ip=2606:4700:a8::7  location=sjc05 protocol=http2
Registered tunnel connection ip=2606:4700:a0::9  location=lax08 protocol=http2
Registered tunnel connection ip=2606:4700:a0::10 location=lax12 protocol=http2
```

**顺手修了一个更严重的问题**：动手前 `ppcat.online` 订阅已经是 **530**
（隧道无活跃连接）——也就是 VPN 订阅当时是坏的。修好隧道后恢复 200。

**守护脚本同步修正**（`tunnel-keepalive.sh`）：原脚本拉起的命令**不带这两个参数**，
所以它每天"成功"拉起一个连不上的进程——`pgrep` 能看到在跑，实际一直是 530，
比不拉更糟。现已改成带参数，并加了「进程在 ≠ 连接正常」的二次确认。

### 实测速度（5 次采样，每次 3MB）

| 次序 | 速度 |
|---|---|
| 1 | 549 KB/s |
| 2 | 284 KB/s |
| 3 | 675 KB/s |
| 4 | 525 KB/s |
| 5 | 971 KB/s |

**平均约 600 KB/s**，波动约 3 倍。

对比 GitHub 直连：本机 60 秒下不完 5MB（**< 83 KB/s**）。

| 源 | 118MB 需要 |
|---|---|
| GitHub | 约 24 分钟以上 |
| 隧道 | 约 **3.5 分钟** |

**快了约 7 倍**，但不是"秒下"。

### 必须说清的风险

1. **依赖本机 7×24 在线**：本机断电/重启，所有用户就下不了
2. **占用本机上行**：每个用户下 118MB，本机就上传 118MB
3. **CF 节点在美国**（sjc05/lax08/lax12）：国内访问要绕一圈
4. **免费隧道无 SLA**：速度波动 3 倍是常态

### 真正的解不是隧道

`update.json` 里本来就有 `patches[]`（差分补丁，**8.6MB**），App 侧
`delta_patch.dart` 也有完整实现。

600 KB/s 下：整包 118MB = 3.5 分钟，**差分 8.6MB = 15 秒**。

所以「更新慢」的根因是**每次都下整包**，不是源不够快。
下一轮该确认的是：为什么差分没生效（补丁只覆盖特定旧版本？还是应用失败回退整包？）。

## 附录 A：外部方案调研结论

调研的目的是**判断可行性**，不是取用代码。所有功能均按本项目结构自行实现。

| 方案 | 结论 | 说明 |
|---|---|---|
| 免密模型聚合通道 | 部分可用 | 免费车道本项目早已自建（`zen-proxy.mjs`）；本周期按同样的接口约定补齐了 3 项工程能力 |
| 手机端 DSH 客户端 | 路线不同 | 对方走 proot + Ubuntu，本项目直嵌 `libnode.so`；见下方对比 |
| 网盘 Agent Skill | 不可用 | 只提供 darwin / linux / windows 五种架构，Android 上没有可执行文件 |
| 侧边栏 web 插件 | 不适用 | React/TypeScript 实现，与本项目 Flutter 原生界面不同栈；只借用了交互思路 |

**关于「113MB vs 需 1GB」**：差别来自运行时路线，不是能力差距。

| | proot + Ubuntu（glibc） | 直嵌 `libnode.so`（bionic） |
|---|---|---|
| 空间 | 需约 1GB 预留 | 113MB 单包 |
| 能跑的本地模型 | glibc 原生包都能跑（含 SenseVoice，239MB） | 受 bionic 限制；本项目改用 `sherpa_onnx`（Android arm64 原生库，配音已在用） |
| 启动 | proot 兼容启动 | 首次解包 40~80 秒，之后离线 |

选直嵌是因为「装完就能用」优先于「什么原生包都能跑」，代价是本地 ASR 要换一条更轻的路。
