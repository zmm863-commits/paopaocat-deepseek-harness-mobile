# 开发周期 0.83.1 —— 空厂家致全部模型不可用（热修）

> 2026-11-05 | 版本：v0.82 → v0.83.1 | 触发：用户真机日志（981 行）

## 1. 起因：一份 14 分钟里 0 次成功建会话的日志

用户交上来一份 `dsh-report`（v0.82 / versionCode 250 / LENOVO TB323FU / Android 16）：
运行 14 分 6 秒，错误 124 条，**成功建立的会话 0 次**，发什么都返回「建会话失败」。

关键的几行：

```
llm-pi-ai (@deepseek-ai/dsh-llm-pi-ai): Error:
  provider "com" has an empty baseURL
dsh: warning: 1 entry did not activate

[acp] session/new 失败，服务端完整返回：
  {"code":-32603,"message":"Internal error",
   "data":{"details":"no adapter registered for provider \"zen\""}}
```

三轮连锁：
1. 一个叫 `com` 的厂家，**0 个模型 / 没有 Key / baseURL 是空的**
2. 它被原样写进了 overlay → 引擎 `resolveProfiles` 抛错 → **整条 `llm-pi-ai` 插件激活失败**
3. 插件没起来 = **一个适配器都没注册**，于是换任何厂家都报 `no adapter registered`

用户的判断是「是不是我选错模型了」，实际跟他选什么完全无关——坏的是**整张 provider 注册表**。

## 2. 根因：过滤算出来了，却没用上

`app/lib/local/dsh_runtime.dart` 的 `writeOverlayFromConfig()` 里，本来就有过滤：

```dart
// 只写"真的有模型"的厂家。
// ⚠️ 这个过滤是必须的：……宁可少写一个空厂家，也不能写坏整份配置。
final emittable = <ProviderSpec>[
  for (final p in providers)
    if (config.models.any((m) => m.provider == p.id)) p,
];
```

但 `emittable` 只被用来算「选中项该回落到谁」，**真正写 overlay 的循环用的还是没过滤的 `providers`**：

```dart
for (final p in providers) {   // ← 写坏整份配置的就是这一行
```

也就是说：作者早就想到过这个坑、写了注释、写了过滤，但**过滤没接到写出那一端**。这类「算出来了但没接上」的缺陷，和本项目另外三个「沉默缺陷」（性能开关从未生效、选择器只修一半、MCP 父环境漏了）是同一类。

## 3. 改动

### 3.1 空厂家不再写进 overlay（致命项）

- `emittable` 的过滤条件加严：`有模型` **且** `baseURL 非空`
- 写出循环 `for (final p in providers)` → `for (final p in emittable)`

两个条件缺一不可：空 `models:` 在 YAML 里是 `null`（校验否掉整份 overlay）；空 `baseURL` 让插件激活失败（本次事故）。

### 3.2 选中的模型被裁掉时回落（防御项，**不是本次事故的原因**）

> ⚠️ 订正：这一节最初写的判断是「用户选中的 `cohere/north-mini-code:free` 在探活后被裁掉了」。实测**不成立**——该模型只存在于 Kilo 通道的清单里（Zen / OVH 的 `/v1/models` 都没有它），代理的 `laneOfModel()` 会正确把它路由到 Kilo，而 Kilo 那条此刻**能正常对话**（实测 1.5 秒返回）。所以用户的选择本身没问题，本次事故的唯一病因是 3.1。

但这条回落**仍然值得加**，因为它是同一类风险的另一半：

旧的路由回落只检查「**厂家**还在不在」，不检查「**型号**还在不在该厂家的清单里」。三条上游合并成一个 `zen` 厂家之后，`zen` 这个厂家永远是"活着"的（只要 kilo 或 ovh 还有货），于是即便某个型号真的被裁掉了，也会被一路放行写进默认路由，报出来的还是上游错误（`model_not_found` / `FreeUsageLimitError`），完全看不出是本地选错了。

所以补一道**模型级**回落：厂家在、但型号不在该厂家清单里 → 落到该厂家第一个模型，并打一行日志说明原因。这次它不是救火的那一刀，是防止下一次「换了个模型名就查半天」。

### 3.3 探活前滤掉非对话模型（噪音项）

上游 `/v1/models` 里混着向量（bge / embedding）、语音识别（whisper）、语音合成（nvr-tts）、文生图（stable-diffusion / sdxl / flux）。拿它们 ping 必然 `model_not_found`——这次一次探活刷出 **50 条**同类错误，把有用信息全淹了。

`zen_proxy.dart` 的 `fetchFreeModels()` 加 `_looksLikeChatModel()` 黑名单过滤。判据刻意保守（**宁可多留也不误杀**）：万一漏掉一个真能用的，它 ping 不通会被自动裁掉，不会造成坏结果。

### 3.4 日志口径对齐（顺手）

`overlay 已重写：N 个厂家` 之前报的是 `providers.length`（全量），而实际写进去的是 `emittable`。排查本次 bug 时日志显示 2 个厂家、overlay 里只有 1 个，差点看错方向。改成报**实际写出**的厂家数与模型数。

## 4.5 把「不可用厂家」揪到用户眼前（0.83 追加）

写 overlay 那侧已经不写空厂家了，但用户在设置页**完全看不出有这么个东西在** —— 他不知道自己有个空厂家，也不知道为什么消息发不出去。所以 0.83 把它做成界面可见：

**模型设置页三处改动**（`model_settings_panel.dart`）：

1. **顶部横幅**：存在不可用厂家时显示红框警告 ——「发现 N 个不可用厂家：xxx」+ 一句危害说明 + **一键清理**按钮（弹一次总确认，批量删除）。
2. **卡片标红**：不可用厂家的边框变红、「已配 Key / 未配 Key」徽标换成红色「不可用」、地址行显示红字「（地址为空 —— 必须删掉或补上地址）」。
3. **识别口径**：`地址为空` **或** `0 个模型`，任一命中即算不可用。

**顺带的代码重构**：原来 `_deleteCustomProvider()` 把「确认框 + busy 守卫 + 落盘」揉在一起，一键清理没法复用 —— 循环里会连弹 N 个确认框，而且它开头的 `if (_anyBusy) return;` 配合内部 `_deleting=true` 会让**第二次调用被守卫直接吃掉**（删了第一个，后面全静默跳过）。所以拆成：

- `_deleteCustomProvider(p)` —— 确认框外壳（单个删除入口，行为不变）
- `_deleteProviderSilently(p, {confirm})` —— 纯落盘，不弹框、不碰 busy 守卫

### ⚠️ 真机复现带出的第二个洞（0.83 已补）

2026-11-05 上真机复现时发现：**上午那版标红/一键清理抓不到这个用户的情况。**

他的坏厂家 `com` 的 id 恰好和**内置的「Command（聚合，推荐）」撞了**。于是：

- `_customProviders()` 按"不在内置清单里"过滤 → 这个条目被当成内置的，**卡片根本不渲染**
- 内置卡又没有删除按钮（删除入口只挂在自定义卡上）

结果：**这个坏厂家在界面上完全不可见、也删不掉**。用户只能干看着整个模型服务坏着，连修的机会都没有。这才是它从老版本一直留到现在的原因。

补两处：

1. `_brokenProviders()` 改成扫 **`_cfg.providers` 全量**，不再只看 `_customProviders()` —— 撞 id 的也照抓，横幅能报出来、能一键清理。
2. 内置卡也接上标红：从 `_cfg.providerOf(id)` 取到的记录若地址为空或 0 模型，边框变红、徽标换「不可用」。

清理动作对内置厂家等于**重置为预设默认**（把那条约记录删掉，地址回到内置值），文案里已写明这一点。

**i18n**：新增 8 条文案（横幅标题/说明/按钮、确认框标题/内容、toast、卡片徽标、空地址行），三张语言表同步，守卫测试 2133 → 2141。

## 4.6 追根（订正版）：不是旧设置页，是**升级迁移**

> ⚠️ 本节最初把根因判成了「旧版模型设置页没校验地址」。用户补了一句关键信息后推翻重来：
> **「他是从 0.81 升级上来的，会话里选择模型的地方就出现了 com 这个空厂家，但设置里看不到。」**
> 下面才是真正对得上的链条。

### 4.6.1 真凶：`readConfig` 的老格式迁移

`data/configured_models.dart` 里，读到老格式（v1）`models.json` 时会做一次迁移。老文件只有顶层
`provider` / `baseUrl`，没有 `providers` 数组，于是代码会「照着顶层字段造一条厂家记录」。原来的写法：

```dart
var legacyProvider = providers.isEmpty
    ? sanitizeProviderId('${decoded['provider'] ?? 'com'}')   // 默认值就是 com
    : null;
if (providers.isEmpty) {
  providers.add(provider(
    id: legacyProvider!,
    label: '${decoded['provider'] ?? legacyProvider}',        // label 也是 com
    baseUrl: '${decoded['baseUrl'] ?? ''}',                   // ← 老文件没这个字段 → 空串
  ));
}
```

**老文件里 `baseUrl` 缺失或为空 → 造出一条 `{ id: com, label: com, baseUrl: "" }`。**

这条记录此后每次写 overlay 都被带上 → 引擎 `llm-pi-ai` 抛
`provider "com" has an empty baseURL` → **整条插件激活失败** → 所有厂家都没有适配器 →
用户看到「会话没能建起来」，换任何模型都一样。

### 4.6.2 为什么两个现象都能对上

| 用户说的 | 为什么 |
|---|---|
| **升级上来才出现** | 只有读到**老格式**文件才会走这段迁移。全新安装的路子是 `ensureModelConfig`，那条有地址兜底（默认 `https://api.commandcode.ai/provider/v1`），不会写空。 |
| **设置里看不到** | `com` 和内置的「Command（聚合，推荐）」**撞了 id**。设置页的 `_customProviders()` 按「不在内置清单里」过滤，把它当内置条目排掉；而内置卡没有删除按钮。于是它在设置页完全隐形、也删不掉，只在会话的模型选择器里露一个「com · 0 个模型」。 |
| **0 个模型** | 老文件的模型列表要么是空的，要么在迁移里没归属上。 |

### 4.6.3 修法（两道）

1. **迁移时地址为空就不造厂家**：老文件 `baseUrl` 缺失/为空 → 不生成厂家记录，打一行日志说明。
   宁可让 providers 留空、交给上层自愈路径用默认端点重建，也绝不落一条让全局瘫痪的记录。
2. **修掉由此暴露的空列表崩溃**：迁移完之后还有一步「补每个模型的归属」，原写法
   `m.copyWith(provider: providers.first.id)` 在 providers 为空时当场抛
   `Bad state: No element`，**整份配置会被当成损坏文件**。改成 providers 为空时直接丢弃那些
   无处可挂的模型（留着只会在选择器里出现指向不存在厂家的死条目）。

回归测试：`test/v1_migration_test.dart`（4 条）——
空 baseUrl 不造厂家 / 缺字段不造厂家 / 有地址照常迁移 / v2 文件不受影响。

### 4.6.4 旧设置页那个洞也一起堵了（虽然不是本次病因）

`ui/settings_page.dart` 的 `_save()` 确实只校验 Key、不校验地址（会话红框里那个「去设置」
打开的就是它）。虽然这位网友不是从这儿踩的，但它同样能造出空地址的厂家，所以一并补上：
地址、provider id、model id 三项都不许空。

## 5.6 追加：Bot 页打不开（0.83.1 / versionCode 252）

第二份网友日志（12:39，v0.82）：

```
dsh-bot | 启动失败：Bad state: 运行时里没有 Bot 种子
        （…/files/dsh/profiles-seed/bottest）—— 这个 App 的运行环境不含 Bot 功能。
```

### 根因：解包版本号从来没跟着内容升

- Bot 种子 `app/profiles-seed/bottest/` 是 **2026-10-17（0.77）** 才加进运行时压缩包的；
- 而决定「要不要重新解包」的 `RUNTIME_VERSION` 从 **2026-10-13（0.73）** 起一直是 `"5"`；
- 解包标记 `.dsh-runtime-5` 存在 → `isRuntimeReady()` 恒真 → **升级永远不重新解包**。

于是 **0.73 ~ 0.76 装过的用户全部中招**：`files/dsh/` 里永远没有那个目录，升到多新的版本 Bot 都打不开。这不是"这个 App 不含 Bot 功能"，是旧树没被替换。

### 修法

1. `RUNTIME_VERSION` **5 → 6**。老用户下次启动走 `hasRuntime && !runtimeCurrent` 那条静默换新路径（`hasRuntime` 只看 `lib/bin.js`，所以**不会被踢回欢迎页** —— 这是 2026-10-19 用户抱怨过的那件事，这次没有复发）。
2. Bot `ensureProfile` 自愈：种子缺但安装包里有 → 当场 `unpackRuntime()` 再试一次。
3. 报错文案改清楚：「旧版本解包留下的」+ 下一步怎么做，不再写成「不含 Bot 功能」。

### 规矩（写进 Kotlin 注释）

> **只要随包运行时的内容变了（新增/删除文件），`RUNTIME_VERSION` 就必须 +1。**
> 否则只有全新安装的人能拿到新内容，所有老用户永远停在旧树上。

这类「版本号没跟内容走」的缺陷和本周期另外几个是同一族：**没有报错、只是静默地不生效**。

## 5.7 ⚠️ 订正：Bot 打不开的真正原因（不是解包版本号）

上一节（5.6）把根因判成「`RUNTIME_VERSION` 从没升过，老用户不重新解包」。用户补了一句
**「他是直接安装 0.82 的新用户」**，这个判断当场作废 —— 全新安装根本没有旧标记。

### 真正的原因：v0.82 **正式发布**的那个 APK，runtime 里没有 Bot 种子

把线上 v0.82 的 Release 资产（`paopaocat-dsh-0.82-arm64.apk`，119,952,861 B）下载拆开对照：

| APK | 包内 `dsh-runtime.zip` | `app/profiles-seed/bottest/` 条目 |
|---|---|---|
| **v0.82 线上发布的那份** | 32.1 MB | **0 条** ❌ |
| `dist/` 里本地那份 0.82（从没发出去） | 32.9 MB | **64 条** ✅ |
| 0.83 / 0.83.1（这次发的） | 32.9 MB | 64 条 ✅ |

也就是说：**发出去的那个包和本地验证过的那个包不是同一个**。线上那份用的是
**只有 anysearch、没有 bottest 种子** 的 runtime 变体（32.1MB），全新安装的用户
装完就没有那个目录，一点 Bot 页必然报错。

三条老的门禁（体积<50MB / 0 条 win32 / 含 anysearch）**全都放行了** ——
因为它们只证明「这是个 Android 的 slim 包」，不证明「功能齐全」。

### 修法：加第④道门禁（这次是真防线）

1. `install/verify-runtime.mjs`：加第④条 —— runtime 里必须有
   `app/profiles-seed/bottest/package.json`，否则 `exit 1`。出包前就拦住。
2. `install/check-release.py`：**拆开成品 APK 里的 runtime 再查一遍** ——
   Bot 种子、anysearch 各一条独立结论。这是最后一道闸，对的是「真正要发的那个文件」。

用线上那个坏包验证新闸：

```
[FAIL] 运行时内容：Bot 种子
结论：**不要发这个包** —— 3 项 FAIL
```

### 教训

- **「本地出过好包」不等于「线上发的就是好包」**。这次就是两个文件不一致，
  而所有校验都只跑在本地那份上。
- 门禁要检查 **App 真正会去读的那个路径**，而不是「包看起来对不对」。
  体积、平台、插件名都是间接判据；`profiles-seed/bottest/package.json` 才是直接判据。
- 以后 App 侧再新增「依赖运行时里某个目录」的功能，`check-release.py` 就要多一条判据。

### `RUNTIME_VERSION` 那次升级还算数吗

算，但**不是这位网友的病因**。它修的是另一个真实存在的隐患：0.73~0.76 装过的用户
解包标记早已存在，0.77 加的 Bot 种子确实永远不会被解出来。两条都要，
只是不能拿它解释这次的事故。

## 6. 一句教训

这次的 bug 不在算法，在**接线**：过滤写了、注释写了、连"写坏整份配置"的警告都写在旁边，唯独没有接到写出那一行。

同类缺陷的共性还是那句老话——**失败是静默的，成功是假设的**。用户看到的不是"配置错了"，而是"发消息没反应"，而真正的错误信息（`provider "com" has an empty baseURL`）藏在 `[acp:stderr]` 里，只有 0.82 才做到 adb 可读。

下次再遇到"换什么模型都不行"，第一件事应该是去看 `1 entry did not activate`，而不是换模型。
