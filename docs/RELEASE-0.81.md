## 二、八项改动（逐项）

> 前六项是开发期做的；**第 7、8 项是真机反馈打出来的**（见文末「真机第二轮」），
> 它们把这一版的主题从「有话说」改成了「**地址真的能用**」。

### 1. 电脑端断线不再是白屏（新）

`lib/local/port_forwarder.dart`

以前上游连不上就 `client.destroy()` → 浏览器一片白或 `ERR_EMPTY_RESPONSE`。
现在转发层自己回一页 **HTTP 502 + 中文说明**：

- 写清三个常见原因（开关关了 / App 被回收 / 换了网络）；
- 写清去哪儿重新打开（`设置 → 移动桌面平台`）；
- 页面里每 3 秒 `HEAD` 一次自己，**只要不再是 502 就自动 reload** ——
  手机一恢复，电脑这边不用手动刷新；
- 判据刻意是「不是 502」而不是「200」：手机刚回来的瞬间上游可能是 401/404，
  那也说明服务活了；
- 不引用任何外部资源（此刻手机可能连网都没了，CDN 一定加载不出来）。

诊断日志节流 60 秒一条（页面自己每 3 秒还会探一次，不然日志会被刷满）。

### 2. 开关过程看得见（新）

`lib/ui/widgets/computer_access_panel.dart`

四段人话 + 已等秒数：
`准备运行环境… → 正在启动 DSH 与设计站… → 正在打开对外端口… → 正在接上设计站…`

用枚举 `_Stage` + `stageText(context)`，**每段都写成 `context.tr('字面量')`** ——
i18n 扫描器只认这个形状；把文案塞进 String 字段再 `tr(_stage!)` 会永远进不了翻译表
（切外语露中文且不报错，项目里踩过同类坑）。

### 3. 扫码打开（新）

`lib/ui/widgets/computer_access_qr.dart`（新文件）+ 面板上的「扫码打开」

一屏给出：二维码 + **能照着敲的大字地址**（`192.168.x.x:端口`）+ 单独一行的 `/?token=…`。

为什么不只给二维码：笔记本有摄像头且装了扫码工具才行，台式机根本没有摄像头。
所以文案写的是「电脑有扫码工具就扫这个码；没有的话照着下面手打」——
不写「扫一下就行」这种半真半假的承诺。

依赖：`qr_flutter ^4.1.0`（纯 Dart，无原生库，不影响 ABI）。

**同一轮里测出来的真 bug（已修）**：两个地址（DSH 网页 + 设计站）同时给的时候，
对话框内容比一屏高，在 800×600 的测试屏上直接报 `RenderFlex overflowed by 21 pixels`
—— 真机小屏 / 横屏会看到黄黑条。content 包了 `SingleChildScrollView`。
这条不是「测试写错了」，是界面真会坏；`test/computer_access_qr_test.dart` 的四个用例
现在同时充当回归。

### 4. 修掉：设计站起不来会把保活服务一起停掉（0.80 引入）

0.80 的 `_apply()` 里，`await WebBridge.stop();` 写在了「设计站启动失败」的
catch 块**里面**（缩进都是乱的）。后果：设计站起不来时，DSH 网页本身还活着，
却把保护它的前台服务停了 → 系统随后回收整个进程 → 电脑端断开。

现在：保活只在**用户自己关开关**时停（挪到 else 分支），catch 块里写明为什么不能停。

### 5. 修掉：英/日/韩界面里「移动桌面平台」整块还是中文（0.80 漏翻）

`check-tables.mjs` 实测 0.80 发布时漏翻 **23 条**（整个「移动桌面平台」面板 +
设置页的组名）。都是 0.80 改名时新写的文案，没进三张表。

本版：补 84 条译文（28 条 × 3 语言），`check-tables` **2032 / 2032 · 0 漂移**，
`i18n_test.dart` 钉住的条目数 2004 → 2032。

### 6. 修掉：App 里的 0.80 更新说明只有 5 条

`changelog.dart` 里 0.80 那条停在开发中途的「网页版做减法 5 条」，
而发布说明是 10 条 —— 用户装完在「关于 → 更新说明」里**看不到「移动桌面平台」这个主角**。

现在补齐到 10 条（口径与 `docs/RELEASE-0.80.md` 一致），日期补 2026-10-29。

## 二点五、真机两轮反馈打出来的两个硬伤（2026-10-30）

### 7. 电脑上打不开手机给的网址（真机截图：`dsh web authentication required`）

用户截图上写着：

```
http://192.168.0.100:45721/?token=CNmbRCcg…
→ dsh web authentication required; reopen the URL printed by dsh web.
```

读了随包运行时里 `dsh-client-connection` 的实现才定下来根因：

```js
function processLaunchToken(owner) {
  const created = encodeBase64Url(randomBytes(SECRET_BYTES)); // 每次进程启动都新生成
  PROCESS_LAUNCH_TOKENS.set(owner, created);
}
```

- `launchToken` 是**进程内随机、没有任何注入口子**（内存 Map 里），所以**DSH 每重启一次，token 就换一把**；
- 认证路径是：`GET /` + `?token=` 且等于当前 launchToken → 303 下发 cookie（`location: "./"`，相对路径）；
- 而 App 有**三个**地方会重启 DSH：切模型、开关电脑访问（原来是 `--trusted-host` 参数变化）、服务自愈。

**所以「复制出来的地址」注定一次就废。** 光固定端口（0.80 已做）不够，token 也得固定。

修法：App 对外只发**自己的固定口令**（`BridgePrefs.token`，与设计站同一个），
转发层在**第一个请求头**里把它换成当前 launchToken 再交给 DSH。
用户手里的地址从此长期有效；别人的 token 原样送上去让 DSH 自己 401（**没有把鉴权打开**）。

### 8. 拨一次开关就重启 DSH，还撞见过起不来

0.80 为了放行 `/api`，带 `--trusted-host <网卡:端口>` **重启** DSH。代价：

- 开关一次 = Bot 页闪一次、正在跑的会话被打断；
- 真机上（11:01）重启后 profile 直接激活失败，面板红一片：
  `Bot 服务启动失败（退出码 1）：file-upload connection / ui-deliverables connection,
  sessionController / bot sessionController, connection` —— 用户点第二次就好了，说明是一次性竞争。

修法：**不再用 `--trusted-host`**。转发层把 `Host` / `Origin` / `Referer` 改写成
`127.0.0.1:<port>`，DSH 认为自己被本机访问，天然放行。

- 开关电脑访问**完全不碰 DSH 进程**（顺带：关的时候也不再重启）；
- 面板加了一层兜底：启动失败**自动重试一次**再报错。

### 顺带：地址的第三样也固定了

真机日志里同一台手机两次开开关，注入的地址一次 `192.168.199.2`、一次 `192.168.1.60`
（热点网卡 vs Wi-Fi，`LanEndpoints.list()` 的默认顺序不保证）。所以 `BridgePrefs`
新增 `dshHost`，**端口 + 网卡 + 口令三样一起记**，下次优先回到上次那张网卡。

### 一个只有实现时才会想到的坑：必须断开长连接

HTTP/1.1 默认 keep-alive，我们只改写**一个连接上的第一个请求头** —— 浏览器会在同一连接上
接着发第二个请求，那一次的 `Host` 是**外部地址**（没被改写）→ DSH 的 browser-trust fence
直接 403，症状是「首页能开、点两下就白」。

所以改写时**强制 `Connection: close`**：服务端每个连接只处理一个请求。代价是页面资源
一个连接一个（局域网无所谓），换来的是不用写「解析 body 才知道下一个头在哪」的状态机。
SSE 与 WebSocket 不受影响（它们本来就是一条长响应）。

## 十、三项收尾（2026-10-30 下午，用户「做完」）

上一轮我列了三件「还没修」的，这一轮做完。

### 10.1 本地 MCP 起不来：把启动旗标与 ACP 对齐

现象（真机日志）：`探活失败：node 提前退出 exit=0` + `诊断：带父环境也起不来 → 不是环境问题`，
**零输出**。而同一个 `libnode.so` 起 ACP 是好的。

已经排除：脚本本身没问题（本机 node 22 跑**同一份** `mcp-office.mjs`、同样三行 JSON，
`initialize` + `tools/list` 正常回，3 个工具，`--expose-internals` 下也正常）、
不是环境变量（诊断探针带父环境一样失败）。

**最大嫌疑并且已修**：`DshRuntime` 的类注释写着四条 Android 硬约束 ——
node 必须以 `--expose-internals` 启动（顶上缺失的原生 addon）、
必须 `--require` 文件系统 shim（SELinux 禁 `link()`）与执行环境 shim（没有 bash）。
ACP 那条路**全带着**，而 MCP 这边的 args **只有脚本路径**，等于裸跑 node。
现在 `mcpServers()` 的 args 与 ACP 对齐（shim 文件真的落盘时才挂）。

**同时把探活做成一次能问清楚的诊断**（这次最缺的就是证据）：
- 进程退出后**多等 300ms** 再读 stderr（`exitCode` 常常比 stderr 管道先到，
  上一版就是因此只留下 `exit=0` 这一句、什么线索都没有）；
- 日志里一并记：脚本**在不在、多大**、完整 `command`、`cwd`；
- stderr 为空时**显式写 `(空)`**，不再让人误以为"没记"。

### 10.2 整页资源：40 个请求的回归测试

`Connection: close`（每连接一个请求）是 0.81 自己引入的机制，风险是
"整页几十个静态资源里，只要有一个请求没被改写，Host 就还是外部地址 → 403"。
新增测试：**40 个连续请求必须全部 200，且上游看到的 40 次 Host 全是
`127.0.0.1:<port>`**，总耗时 < 10s。等于把"首页能开、点两下就白"这条真机症状
钉成了测试。

### 10.3 检查更新：串行等超时 → 并发先回先用

原来串行：先 raw，等它**超时 8 秒**才轮到 jsDelivr。真机日志里每次启动都这样
（`source failed … 超时` 紧跟 `ok source=cdn.jsdelivr.net`）。
现在两个源**同时发、谁先回用谁**：raw 通（实测 0.47s）大概率先回，新鲜度不丢；
raw 不通就直接被 jsDelivr（2.16s）兜住。单源（用户自填镜像）仍走原来的单发。
默认超时 8s → **5s**（并发后它只决定"多久判全失败"）。

测试：原有的"三条都失败"用例改成**不按下标断言**（并发下顺序不定，
只要求三种原因都留痕），另加一条并发回归：**慢源排前面也必须 2 秒内拿到快源的结果**。
